# Phase D Implementation Prompt: Appearance Suggestion Flow

Use this prompt to implement Phase D of the character and scene generation cleanup.

## Context

Phase A added `appearanceDescription` to each character record as the stable, tutor-editable physical identity field.

Phase B cleaned up character extraction so AI-generated story-context notes are no longer appended to visible character notes or reusable note tags.

Phase C redesigned the Characters stage so each character card has an editable `Appearance description` textarea wired to `character.appearanceDescription`.

The next step is to add a real, controlled update flow that can draft or refresh the appearance description for a character. The user should remain in control: the generated text should update the editable textarea, not immediately generate a character image and not silently approve anything.

## Phase D Goal

Add an `Update appearance` flow that generates a concise, editable physical appearance description for a single character.

The flow should:

- Save the current lesson before calling the backend.
- Ask the backend to draft or refresh `appearanceDescription` for one character.
- Use the locked story and character basics only as context.
- Avoid lesson vocabulary, scene actions, scene clothing, educational labels and vague image-prompt tags.
- Update the saved character's `appearanceDescription`.
- Return the updated lesson to the frontend.
- Leave the textarea editable after the update.
- Mark existing generated/approved character images stale when the appearance description changes.

## Scope

Implement Phase D only.

Do not implement:

- Character image prompt cleanup.
- Scene image prompt cleanup.
- Scene data model changes.
- Scene-specific clothing, pose or expression fields.
- Generating character images from the new appearance description.
- Automatically regenerating a character image after updating appearance.
- Automatically approving any character image.
- Export changes.
- ZIP generation.
- PowerPoint generation.
- Worksheet generation.
- Audio or video generation.
- Accounts, Firebase, auth, cloud sync, remote storage, hosted publishing or sharing.

Phase D may add:

- Backend appearance prompt/schema/service logic.
- Backend route for updating one character appearance description.
- Frontend API client for that route.
- Frontend `Update appearance` button and loading/error state.
- Tests for the new backend and frontend flow.

## Product Boundary

`appearanceDescription` describes stable physical identity:

- Hair length, colour and broad style.
- Eye colour if useful.
- Approximate height.
- Approximate build.
- Skin tone or complexion if specified or contextually appropriate.
- Age presentation.
- Facial features.
- Distinctive stable physical features.

It should not describe:

- What the character is doing in a specific scene.
- Scene location.
- Temporary pose.
- Temporary expression.
- Scene-specific clothing.
- Props.
- Lesson vocabulary.
- Learner level.
- Educational tone.
- Personality labels such as `friendly`.
- Vague image-control tags such as `clear face`.
- Continuity commands such as `same outfit each image`.

The generated appearance is a draft. The tutor can edit it before image generation.

## Expected User Experience

In the Characters stage:

1. Each character card has the editable `Appearance description` textarea from Phase C.
2. Add an `Update appearance` button near that textarea or near the character image actions.
3. Clicking it saves the current lesson if needed.
4. While the request is running, the button shows a loading state such as `Updating appearance...`.
5. The character card is disabled consistently with existing character operations.
6. On success, the textarea updates with the generated appearance description.
7. The user can immediately edit the generated text.
8. If the character already had a generated or approved image and the text changed, the character is marked stale and approval is cleared.
9. If the request fails, show an inline error on that character card.
10. No image is generated by this action.

## Backend API Contract

Add a backend route under the existing character routes.

Recommended endpoint:

```text
POST /api/characters/appearance
```

Recommended request:

```json
{
  "lessonId": "lesson-20260911-example",
  "characterId": "character-marta"
}
```

Recommended success response:

```json
{
  "lesson": {
    "...": "updated saved lesson"
  },
  "appearance": {
    "characterId": "character-marta",
    "appearanceDescription": "Woman in her mid 30s with shoulder-length dark brown hair, brown eyes, light skin and an average build.",
    "generatedAt": "2026-09-11T15:00:00.000Z",
    "model": "gpt-5-mini",
    "promptVersion": "character-appearance-v1"
  }
}
```

Recommended error behavior:

- `400` for missing `lessonId`.
- `400` for missing `characterId`.
- `400` for malformed `characterId`.
- `404` for missing project or missing character.
- `422` for invalid saved lesson shape.
- `422` for draft/unlocked story if the implementation requires a locked story.
- `503` for missing OpenAI configuration or provider failure.
- `500` only for unexpected server errors.

Keep errors JSON and consistent with existing character/image route conventions.

## Backend Implementation Steps

### 1. Create A Prompt Builder

Create a prompt builder for appearance description generation.

Recommended file:

```text
server/src/prompts/characterAppearancePrompts.js
```

Export:

```js
export const characterAppearancePromptVersion = "character-appearance-v1";

export function buildCharacterAppearancePrompt(lesson, character) {
  // returns OpenAI Responses input
}
```

The prompt should ask for one concise physical appearance description.

It should include:

- Character name.
- Role.
- Age or age range.
- Sex or gender.
- Background or nationality, carefully framed as optional context.
- Existing `appearanceDescription`, if any.
- Lesson setting and scenario only as weak context.
- Locked story sentences only to understand recurring character context, not to extract scene actions.

It should instruct:

- Output stable physical appearance only.
- Use one plain sentence or two short sentences.
- Stay concise.
- Do not mention the character's name unless natural.
- Do not mention the lesson, learner level, story, classroom, image generation, or prompt.
- Do not include bullets, labels, Markdown or commentary.
- Do not include scene-specific clothing, pose, expression, action, location or props.
- Do not include vague traits such as `friendly`, `clear face`, `adult learner context`.
- Do not include continuity commands such as `same outfit each image`.
- Do not include medical, appointment or vocabulary words unless they are genuinely physical traits, which they usually are not.
- Do not infer sensitive traits beyond what the tutor/setup already states.

Example prompt instruction:

```text
Write a stable physical appearance description for this recurring lesson character.
Describe only physical identity that can remain consistent across scenes.
Avoid clothing unless it is a permanent defining feature.
```

### 2. Create A Response Schema

Add a strict response schema.

Recommended file:

```text
server/src/schemas/characterAppearanceSchemas.js
```

Recommended schema:

```js
export const characterAppearanceSchemaVersion = "character-appearance-v1";

export const characterAppearanceResponseFormat = {
  type: "json_schema",
  name: "character_appearance",
  strict: true,
  schema: {
    type: "object",
    additionalProperties: false,
    properties: {
      appearanceDescription: {
        type: "string",
        description: "Concise stable physical appearance description only."
      }
    },
    required: ["appearanceDescription"]
  }
};
```

Keep the schema small. Do not add hair/eyes/build fields in Phase D.

### 3. Create Validation For Appearance Responses

Create or add a validator for the appearance response.

Recommended behavior:

- Parse JSON from Responses output.
- Require `appearanceDescription` to be a string.
- Trim and collapse whitespace.
- Reject empty output.
- Enforce the existing maximum from Phase A, recommended `600` characters.
- Prefer a shorter practical range, but do not reject useful text merely because it has two sentences.
- Reject obvious non-appearance boilerplate such as Markdown bullets, labels, JSON fragments in the text, or phrases like `learner level`.
- Reject known noisy terms when they appear as standalone vague tags:
  - `clear face`
  - `adult learner context`
  - `same outfit each image`
- Avoid brittle over-filtering that would reject legitimate physical descriptions.

Recommended exported helpers:

```js
export class CharacterAppearanceValidationError extends Error {}
export function parseCharacterAppearanceResponse(text) {}
export function validateCharacterAppearanceResponse(value) {}
```

Use existing validation style from `validateCharacterExtraction.js` or story validation.

### 4. Create Appearance Service

Recommended file:

```text
server/src/services/characterAppearanceService.js
```

Recommended export:

```js
export async function updateCharacterAppearanceForProject(
  lessonId,
  characterId,
  options = {}
) {}
```

Service responsibilities:

1. Validate `lessonId`.
2. Validate `characterId` using the existing safe record ID pattern/helper if available.
3. Load the saved project.
4. Validate lesson shape.
5. Optionally require locked story status and valid locked story snapshot.
6. Find the character.
7. Require character name.
8. Build the appearance prompt.
9. Call the OpenAI Responses API using the story/text model, not the image model.
10. Parse and validate response.
11. Update only the target character's `appearanceDescription`.
12. Preserve all other character fields.
13. Mark existing generated/approved image state stale if the description changed.
14. Save the updated project.
15. Return the updated lesson and appearance metadata.

Use `getStoryModel()` unless there is already a better text-generation model selector.

Use `getOpenAIClient("Character appearance generation")`.

Do not call `images.generate`.

### 5. Backend Stale Marking

Because the backend will update the saved lesson directly, it must perform stale marking too. Do not rely only on frontend helper logic.

When `appearanceDescription` changes and the character has generated image work:

- Preserve `imagePath`.
- Preserve `generationCount`.
- Set `approved: false`.
- Set `stale: true`.
- Set `staleReason: "Character appearance changed after image generation."` or reuse the established character stale reason if consistency requires it.
- Set `staleAt` to `now`.
- Keep `generationStatus` compatible with existing generated-image behavior, typically `generated` if an image path exists.

When there is no generated image work:

- Update `appearanceDescription`.
- Do not mark stale.

If the generated appearance is identical to the current normalized description:

- Do not mark stale solely because the operation ran.
- Still return success metadata.

### 11. Interaction With Manual Edits

The generated description replaces the current `appearanceDescription` on success.

This is acceptable because the user explicitly clicked `Update appearance`.

However:

- Save current manual edits before requesting an update.
- Do not update any other character.
- Do not update legacy notes.
- Do not update image style.
- Do not update scene records.

If the user manually edits the appearance while the request is in flight, prefer the existing operation-lock behavior by disabling the card during the request. Do not attempt complex merge conflict behavior in Phase D.
